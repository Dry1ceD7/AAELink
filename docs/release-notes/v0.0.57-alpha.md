# v0.0.57-alpha — Versioned migration runner (Camp A, release 1 of 3)

**Released:** 2026-05-19

First of three releases that move `lib/migrate.ts` from a 2,402-line idempotent blob into a proper versioned-migration system. This release adds the runner mechanism only — **no schema changes**. The existing `migrate.ts` body is wrapped verbatim as `001_initial_schema`. Existing populated databases (dev, staging, any prod) are auto-detected and recorded as already-applied without re-running anything.

Built per the brainstorm + plan in `docs/superpowers/brainstorms/2026-05-19-migrate-split.md` and `docs/superpowers/plans/2026-05-19-migrate-split.md`. TDD discipline: 8 tests written first against a stub Pool, watched fail, then the runner implemented to make them pass.

## What changed

### New module: `lib/migrationRunner.ts` (~140 LOC)

Public surface:

```ts
export interface Migration {
  id: string                                     // 'NNN_short_snake_case'
  up: (pool: RunnerPool) => Promise<void>
}
export interface RunnerPool {
  query(text: string, params?: unknown[]): Promise<{ rows: unknown[] }>
}
export async function ensureMigrations(
  pool: RunnerPool,
  migrations: readonly Migration[]
): Promise<{ applied: string[]; alreadyApplied: string[] }>
```

Behavior pinned by tests:

- **Bookkeeping** — creates `aaelink.schema_migrations(id TEXT PK, applied_at BIGINT)` on first run.
- **Idempotent re-run** — reads the recorded ids, runs only the migrations not yet applied, returns both lists.
- **Failure** — a migration that throws aborts the run; subsequent migrations don't run; the failing migration is not recorded.
- **Order respected by array, not by id** — the runner trusts the caller's order.
- **Synthetic baseline** — if the legacy schema is detected (via `to_regclass('aaelink.users')`) AND `schema_migrations` has zero rows, the runner records `001_initial_schema` as already-applied without running it. Makes the v0.0.57 deploy safe on every existing database.
- **Concurrent boot safety** — `pg_advisory_lock` (key `0x41454c4d`, 'AELM') around the run. Released on completion or error via `try/finally`. The unlock itself is best-effort: if the connection is dead, the lock expires with the session.
- **Forward-only** — no `down()` API. Renames and column-type changes go through add → backfill → drop over multiple deploys.

### `lib/migrate.ts` — wrapped, no schema change

The existing `run()` body is now the body of `migration001InitialSchema(pool)`. The new top-level `run()` does just:

1. `CREATE SCHEMA IF NOT EXISTS aaelink;`  (must exist before the runner creates `schema_migrations` inside it)
2. `await ensureMigrations(pool, MIGRATIONS)` where `MIGRATIONS = [{ id: '001_initial_schema', up: migration001InitialSchema }]`

Two small type fixes were needed to make the existing legacy code work against the structural `RunnerPool` interface:

- `ensureGlobalWorkspaceAndDepartments(pool)` parameter retyped from `import('pg').Pool` to `RunnerPool`. The function only uses `pool.query`, so no runtime change.
- One unsafe `wsRows[0].id` access narrowed via `as { id: string }`. (RunnerPool returns `unknown[]` for `rows`; the original code implicitly trusted `pg`'s typing.)

The legacy `migrateOnce` cache + the failure cache-bust are preserved unchanged.

### New tests: `tests/migrationRunner.test.ts` (8 tests, TDD)

Each block was written first, watched fail with a "Cannot find package '@/lib/migrationRunner'" error, then the implementation written in one pass, then the suite re-run to GREEN.

1. Bootstrap a fresh database — runs every migration in order, records each.
2. Idempotent re-run — same setup, runs zero migrations, returns full `alreadyApplied` list.
3. Partial-applied-then-tail — `001` already applied, runs `002` and `003` only.
4. Failure stops further migrations — `002` throws, `003` doesn't run, `002` not recorded.
5. Synthetic baseline applies on legacy schema — `001_initial_schema` recorded without invoking.
6. Synthetic baseline does NOT trigger when migrations are already recorded — runs the not-yet-applied tail normally.
7. Order respected by array — `[zzz, aaa]` runs zzz first.
8. `schema_migrations` table is ensured before any reads.

### New doc: `lib/MIGRATIONS.md`

Contributor doc covering the forward-only contract, naming convention, synthetic baseline, and how to tear down + re-run from scratch on a dev box (`DROP SCHEMA aaelink CASCADE;` then restart).

## What this enables

- **v0.0.58** can carve the messaging domain out of `001_initial_schema` into a separate numbered migration (`002_messaging`) and a cleanup migration (`003_drop_redundant_indexes`) that drops the 16 redundant indexes the audit identified. Each new migration is reviewable in <10 min.
- **v0.0.59** can carve the remaining domains (auth, support, webhooks, audit, ticketing, KB, integrations).
- A future Postgres CI integration test can verify a fresh database boots cleanly with the same outcome as a synthetic-baseline production database.

- **Splitting `001` into per-domain migrations** — v0.0.58.
- **Dropping the 16 redundant indexes** — v0.0.58 in `003_drop_redundant_indexes`.
- **Real-Postgres CI integration test** — v0.0.58. The unit-test stub pool covers ordering, idempotence, baseline, and failure handling; advisory-lock semantics need a real Postgres to verify and that test goes in v0.0.58.
