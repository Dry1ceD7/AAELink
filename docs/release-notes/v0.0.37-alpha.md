# v0.0.37-alpha — Redis Streams replay store

**Released:** 2026-05-18

Closes the v0.0.36 follow-on item: cross-pod replay coverage. The `MemoryReplayStore` shipped at v0.0.36 lives in process memory, so a client that reconnects to a different gateway pod from where it disconnected gets nothing back from `since`. This release adds `RedisStreamsReplayStore`, a swap-in implementation of the same `ReplayStore` interface that uses Redis Streams (`XADD MAXLEN ~ N`, `XRANGE`) for shared retention.

The boot script now picks the store based on `REDIS_URL`: when set, the gateway uses Redis Streams; when unset, it falls back to the per-pod memory store from v0.0.36. No protocol or router changes.

## What changed

### New: `lib/wsGateway/redisStreamsReplay.ts`

```typescript
export class RedisStreamsReplayStore implements ReplayStore {
  // One Redis stream per topic, key = `${prefix}${topic}`
  // XADD <key> MAXLEN ~ N * event <json>     — append + bounded retention
  // XRANGE <key> (cursor +                    — fetch strictly after cursor
}
```

The cursor returned from `record()` is the native Redis stream id (`<ms>-<seq>`). On `since(topic, cursor)` the store calls `XRANGE` with `(<cursor>` as the start (Redis's "exclusive" prefix) so callers receive only entries strictly after the supplied cursor — same semantics as `MemoryReplayStore`.

The `MAXLEN ~ N` (approximate trim) keeps the buffer size bounded with no client coordination; Redis trims at insertion time, may keep a few extra entries for performance, and the store treats that as acceptable. Real per-topic ceiling is `maxPerTopic` ± O(64).

### New: `wrapIoredisStream(client)` in `lib/redisClientFactory.ts`

Encapsulates the `XADD MAXLEN ~ N * field value` argument layout so the store stays free of `ioredis`-specific concerns. Production deployments that already have `ioredis` installed for pub/sub also get the streams adapter for free.

### Updated: `scripts/wsGateway.ts`

Boot decision tree:

```
if REDIS_URL is set:
  try {
    construct ioredis client
    use RedisStreamsReplayStore
    log "Replay store: redis_streams"
  } catch (e) {
    log warning
    fall back to MemoryReplayStore
  }
else:
  use MemoryReplayStore
  log "Replay store: memory"
```

The pod logs the chosen backend at startup so operators can verify multi-pod replay coverage is wired correctly.

## TDD discipline

`tests/wsGateway/redisStreamsReplay.test.ts` (7 tests) pin the store contract against a hand-rolled `FakeStream` that mirrors the subset of `XADD` / `XRANGE` we use:

- record + since(0) round-trip
- preserves record order
- since-cursor filtering returns only entries strictly after the cursor
- topic isolation (each topic maps to its own stream key)
- empty list for unknown topics
- bounded retention via approximate trim — newest entry always present, total never exceeds the cap
- malformed event JSON in the stream is treated as a no-op (defensive against operator-injected garbage or schema drift)

Real Redis behavior is exercised in production; the unit tests cover the abstraction contract.

## Operations notes

**To enable cross-pod replay in production:**

```bash
npm install ws ioredis    # already required from v0.0.34/v0.0.35
REDIS_URL=redis://your-redis:6379 \
WS_REPLAY_MAX_PER_TOPIC=2000 \
WS_REPLAY_PREFIX=aae:replay: \
  npm run ws:gateway
```

**Liveness check:** `GET http://gateway:3041/` — the `backend` field returns the pub/sub adapter ("memory" or "redis"); the replay store choice is logged at startup but not exposed via HTTP today.

**Redis memory budget:** ~`max_concurrent_topics × maxPerTopic × avg_event_size`. For a 1,000-channel workspace at default 1,000-events-per-topic and 200-byte events, plan ~200 MB. `XADD MAXLEN ~` enforces the per-topic ceiling; total memory scales linearly with active channels.

## Out of scope (deferred)

- **Stream trimming policy.** Today every pod calls `XADD MAXLEN ~`; Redis does the work. A "leader pod runs `XTRIM` periodically" pattern could reduce the per-write overhead but is unnecessary at current scale.
- **Per-topic retention overrides.** All topics get the same `maxPerTopic`. A future release can accept per-topic overrides if specific channels need more history (e.g. high-traffic announce channels vs. quiet DMs).
- **Stream-id collision across pods.** Redis assigns ids inside the broker, so multiple pods writing to the same stream get globally-monotonic ids automatically. No further coordination needed.
