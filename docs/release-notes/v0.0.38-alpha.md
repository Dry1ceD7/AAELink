# v0.0.38-alpha — browser WS client + cursor management

**Released:** 2026-05-18

Closes the v0.0.37 follow-on item: client-side `since` cursor management. The gateway, replay store, and Redis Streams adapter all shipped in v0.0.34–v0.0.37, but the browser was still talking SSE only — replay was dark code. This release ships the WebSocket client that closes the loop and gives users the actual reconnect-with-no-gap experience.

The release is library-only — `connectCollab()` in `lib/realtime.ts` keeps its SSE behavior, and the new `connectWsCollab()` will be wired in by `app/home/page.tsx` in a follow-on patch (the home shell is the one consumer that has cursor-state to manage). Shipping the library here lets the integration be reviewed independently.

## What changed

### New: `lib/wsClient.ts`

Pure protocol surface (`parseServerFrame`, `serializeClientFrame`, exported types) plus a browser-only `connectWsCollab(opts)` connection helper. Frame shapes mirror the gateway's `lib/wsGateway/protocol.ts`; they're duplicated here on purpose so the client module is fetchable on its own without dragging in `redisPubSub.ts` or any other server-only transitive imports.

The `connectWsCollab` helper handles:

- WebSocket construction with `ws://` or `wss://` URLs from `NEXT_PUBLIC_WS_GATEWAY_URL`
- Auto-reconnect with linear backoff (700 ms × min(attempt, 5), capped at 8 attempts)
- Heartbeat ping every 30 s
- Per-topic cursor tracking — every received `event` frame's `id` is stashed; on reconnect the client sends `subscribe(channel, since: cursor)` so the gateway flushes the v0.0.36/v0.0.37 replay store and the user sees no gap
- Multi-channel subscribe/unsubscribe via the returned handle
- Status callback (`onConnected(true|false)`) for UI

API surface:

```typescript
const handle = connectWsCollab({
  url: 'wss://ws.aaelink.example.com/ws',
  channelId: 'ch-1',
  onEvent: ({ id, payload, replay }) => { … },
  onConnected: (connected) => { … },
})
handle.subscribe('ch-2')           // join an additional channel
handle.cursors()                   // { 'channel:ch-1': '0-42', 'channel:ch-2': '0-15' }
handle.close()                     // disposes everything
```

### TDD discipline

`tests/wsClient.test.ts` (14 tests) pin the parser/serializer:

- All four `ServerFrameIn` variants parse correctly (`hello`, `pong`, `event`, `error`)
- `event.replay` defaults to `false` when the field is absent
- Malformed JSON, unknown types, missing/non-string topic, missing id, non-object payload all return `null`
- All three `ClientFrameOut` variants serialize correctly (`subscribe` with/without `since`, `unsubscribe`, `ping`)
- Type-level check that the discriminated union is correctly shaped

The connection lifecycle (auto-reconnect, ping, cursor tracking) is exercised by browser E2E in subsequent releases — mocking `WebSocket` reliably is more brittle than running the real thing through Playwright.

## Out of scope (deferred)

- **Wiring into `lib/realtime.ts` / `connectCollab()`.** That function's existing `getSinceMs: () => number` callback expects millisecond timestamps; the gateway uses opaque cursor strings. Threading the new shape through the existing API would be a breaking change to dozens of callers. The home shell's WS path will be a parallel `connectWsCollab` flow that uses the new cursor model directly.
- **`NEXT_PUBLIC_WS_GATEWAY_URL` documentation in `.env.example`.** The server-side `WS_GATEWAY_URL` is already documented; the public-prefixed mirror needs to be added when v0.0.39 wires the home shell — it's not yet read anywhere.
- **Client-side fallback orchestration.** Today, picking WS vs. SSE will be a hard gate at the home shell mount: if `NEXT_PUBLIC_WS_GATEWAY_URL` is set, use WS; if not, use SSE. Mid-session fallback (WS fails repeatedly → switch to SSE) is more complex and is tracked separately.
