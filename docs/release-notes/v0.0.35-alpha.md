# v0.0.35-alpha — WebSocket gateway service

**Released:** 2026-05-18

Closes the second half of audit §1.1 / §2.1: the WS gateway service. v0.0.34 wired Redis pub/sub auto-connect; this release ships the standalone Node + `ws` process that subscribes to that bus and fans out to connected browsers. `app/api/ws/route.ts` continues to advertise the gateway's URL via `WS_GATEWAY_URL`; the SSE path remains the supported fallback for any client that can't reach the gateway.

## Architecture

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│  Browser A  │    │  Browser B  │    │  Browser C  │
└──────┬──────┘    └──────┬──────┘    └──────┬──────┘
       │ wss://            │ wss://           │ wss://
       │                   │                  │
       └────────┬──────────┴──────────────────┘
                ▼
       ┌────────────────────┐
       │   wsGateway (LB)   │   <-- N processes behind a load balancer
       └────────┬───────────┘
                │ pub/sub
                ▼
        ┌──────────────┐
        │    Redis     │
        └──────────────┘
                ▲
                │ pub/sub
       ┌────────┴───────────┐
       │   Next.js (LB)     │   <-- M processes; publish on mutation routes
       └────────────────────┘
```

The gateway and the Next.js app share the same `lib/redisPubSub.ts` adapter; both call `getPubSubAsync()` so they get the same `RedisPubSub` instance after the v0.0.34 connect lands. Gateway-only changes:

- `lib/wsGateway/protocol.ts` — JSON envelope schema; pure parser/serializer with permissive forward-compatibility (unknown extra fields are silently dropped).
- `lib/wsGateway/router.ts` — per-connection state machine; subscribes/unsubscribes against an injected `PubSubAdapter`; transport-agnostic via a small `OutboundSocket` interface (`{ send, close }`).
- `scripts/wsGateway.ts` — boot script that lazily imports `ws` (so the package stays opt-in like `ioredis`), validates session cookies on `upgrade`, then hands the WebSocket to the router.
- `lib/session.ts` — new `readSessionUserIdFromCookieHeader(header)` for the gateway's HTTP-server context (the existing `readSessionUserId()` depends on Next.js's `cookies()` helper, which isn't available in plain Node).
- `package.json` — `npm run ws:gateway` and `npm run ws:gateway:dev` (watch mode) added.

## Wire protocol

**Client → Server frames:**

```json
{ "type": "subscribe",   "channel_id": "ch-1" }
{ "type": "unsubscribe", "channel_id": "ch-1" }
{ "type": "ping" }
```

**Server → Client frames:**

```json
{ "type": "hello", "user_id": "u-1" }
{ "type": "event", "topic": "channel:ch-1", "payload": <PubSubEvent> }
{ "type": "pong" }
{ "type": "error", "code": "invalid_frame", "message": "Frame could not be parsed." }
```

Auth: session cookie validated **once at upgrade time**. Long-lived connections do not re-validate; expiring tokens take effect on the next reconnect. The gateway does not accept message-publish frames from clients today — publishing remains an HTTP `POST /api/ws` (or any mutation route) to the Next.js app, which then publishes to Redis. This keeps the audit-log + CSRF + rate-limit chain intact.

## TDD discipline

## Operations notes

**To run the gateway in development:**

```bash
npm install ws ioredis    # add the runtime-optional packages
REDIS_URL=redis://localhost:6379 \
WS_GATEWAY_PORT=3041 \
  npm run ws:gateway:dev

# In a second terminal, the Next.js app advertises the gateway URL:
WS_GATEWAY_URL=ws://localhost:3041/ws npm run dev
```

**Liveness check:** `GET http://localhost:3041/` returns `{"status":"ok","backend":"redis"}` (or `"memory"` in fallback mode).

**Production deployment shape:**

- One `wsGateway` Pod per ~2,000 expected concurrent WS connections (the per-process ceiling depends on Linux `ulimit -n` and the host's TCP buffer budget; `ws` itself can serve tens of thousands of connections per process).
- Sticky sessions are **not** required: each connection is an independent state machine, and subscription state lives only in the gateway process. A reconnect picks any gateway pod.
- The Next.js app does not need to know about the gateway pods; it only publishes to Redis. The gateway pods do the fan-out.

## Out of scope (deferred)

- Adding `ws` to `package.json`. Production deployers add it to their root `dependencies`. Like `ioredis`, the package is intentionally optional so unit-test and dev-without-multi-node deployments stay clean.
- TLS termination at the gateway. Run behind nginx / an LB that terminates wss:// and forwards plain ws:// to the gateway pod. The gateway listens on plain HTTP for that reason.
- Inbound publish frames. Clients send messages via the existing HTTP routes; the gateway is read-only from the client's perspective. This avoids duplicating the audit-log + CSRF + rate-limit logic on both sides.
