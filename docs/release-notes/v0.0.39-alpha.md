# v0.0.39-alpha — home shell speaks WebSocket

**Released:** 2026-05-19

The realtime stack from v0.0.34 → v0.0.38 was end-to-end correct on the wire and dark to users — the home shell still opened SSE and ignored the gateway. This release wires `connectWsCollab` from v0.0.38 into `app/home/page.tsx`, completes the user-visible loop, and lights up the replay store: when a connection drops and reconnects, the events sent during the disconnect window arrive replayed instead of dropped.

## What changed

### `app/home/page.tsx`

The realtime hook now switches on `process.env.NEXT_PUBLIC_WS_GATEWAY_URL`:

- **Set:** open a WebSocket via `connectWsCollab(...)`. Map gateway events into the existing `onIncoming` / `onDeletions` handlers — `event.payload.type === 'message'` becomes `onIncoming([post])`, `'deletion'` becomes `onDeletions([{ id, deleted_at }])`. The cursor (`id` field on each event frame) is tracked per-topic by `wsClient` so reconnects send `subscribe(channel, since=last_id)`. The browser sees the SSE-poll fallback's "Connecting" UI replaced with a single steady WS connection that reconnects with linear backoff.
- **Unset:** continue with the existing `connectCollab(...)` SSE-or-poll path. No behavior change for current deployments.

The `'message'` payload coercion is defensive — gateway frames carry `payload: unknown`, and the home shell now validates the shape before pushing into `setPosts`. A malformed server frame can never crash the timeline.

The other `PubSubEvent` variants (`typing`, `presence`, `reaction`, `thread_update`, `read_state`, `channel_update`, `notification`) are not yet wired; they flow through dedicated channels in the existing UI today and will be migrated in subsequent releases as each subsystem gets its own WS hook.

### `.env.example`

`NEXT_PUBLIC_WS_GATEWAY_URL` documented alongside the existing `WS_GATEWAY_URL`. Without the public mirror, the browser stays on SSE — that's the explicit opt-in gate.

## Operations notes

**To enable the WS path in production:**

```bash
# 1. Run the gateway service (from v0.0.35) on a sidecar pod or its own host
WS_GATEWAY_PORT=3041 \
REDIS_URL=redis://your-redis:6379 \
WS_REPLAY_MAX_PER_TOPIC=2000 \
  npm run ws:gateway

# 2. Set the public URL the browser will dial
NEXT_PUBLIC_WS_GATEWAY_URL=wss://ws.aaelink.example.com/ws \
  npm run start
```

The browser bundle reads `NEXT_PUBLIC_WS_GATEWAY_URL` at build time. Setting it at runtime requires a rebuild.

**Roll-out shape:** flag a single workspace by deploying a build with the env var set; verify reconnect-with-replay works end-to-end (pull the network cable, reconnect, see the missed messages arrive without the SSE poll round-trip); then enable globally by rebuilding all pods with the same env var.

**Roll-back shape:** unset `NEXT_PUBLIC_WS_GATEWAY_URL` and rebuild. The SSE/poll fallback is unchanged from v0.0.33.

## Out of scope (deferred)

- **Mid-session WS-to-SSE downgrade.** If the WS gateway is unreachable, the page shell stays in WS reconnect attempts (capped at 8 in `wsClient`). After the cap, the WS path goes idle. Production deployers should treat the gateway as a hard dependency when `NEXT_PUBLIC_WS_GATEWAY_URL` is set; mid-session fallback is more complex and tracked separately.
- **Cursor persistence across full page reloads.** `wsClient.cursors()` is in-memory; a hard reload starts at `since=0` and gets a full replay window. The replay store's bounded retention prevents this from flooding the client (default 1,000 events per topic). Persisting cursors to localStorage is a small follow-on if the replay-storm becomes user-noticeable.
- **Migrating SSE consumers.** `lib/realtime.ts` `connectCollab()` is unchanged. Other components that build their own `EventSource` (admin metrics, observability streams) continue to do so. They'll be migrated piecemeal as each owner picks up the WS pattern.
