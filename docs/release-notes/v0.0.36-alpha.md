# v0.0.36-alpha — replay-on-reconnect

**Released:** 2026-05-18

Closes the v0.0.35 follow-on item from `docs/audit-2026-05-18.md` §2.1: when a WebSocket client reconnects after a network blip, the gateway now replays the events the client missed during disconnect instead of leaving the client to fall back to the SSE poll cursor (which works but adds 2.5 s of latency on every reconnect).

The shape ships in two pieces — a small `ReplayStore` interface so the v0.0.37 Redis Streams adapter can swap in without touching the router, and a `MemoryReplayStore` implementation that runs in-process today.

## What changed

### New: `lib/wsGateway/replay.ts`

```typescript
export interface ReplayStore {
  record(topic: string, event: PubSubEvent): Promise<string>
  since(topic: string, since: string): Promise<ReplayEntry[]>
}

export class MemoryReplayStore implements ReplayStore {
  // Per-topic ring buffer; oldest-first eviction at maxPerTopic (default 1000)

```

Cursors are opaque to the caller. The memory store uses a monotonic counter for ordering; the upcoming Redis Streams adapter will use the native stream ID (`<ms>-<seq>`) — the interface stays the same.

### Updated: `lib/wsGateway/protocol.ts`

The `subscribe` client frame now accepts an optional `since` cursor:

```json
{ "type": "subscribe", "channel_id": "ch-1", "since": "0000…0042" }
```

The `event` server frame gained a required `id` (the cursor for that event) and an optional `replay: true` flag so clients can distinguish replay from live events for UI purposes (e.g., suppress notification chimes on replay):

```json
{ "type": "event", "topic": "channel:ch-1", "id": "0000…0043",
  "payload": { ... }, "replay": true }
```

### Updated: `lib/wsGateway/router.ts`

`createConnection` now accepts an optional `replay: ReplayStore`. On `subscribe(channel, since?)`:

1. Subscribes to the live pub/sub stream first (so any events that arrive during the replay query are still captured).
2. Buffers live events while the replay flush is in flight.
3. Calls `replay.since(topic, since)` and emits each missed event with `replay: true`.
4. Drains the buffer of live events (in order) once the replay completes.
5. Switches to direct live-stream emission for subsequent events.

The order is: replay events first (oldest → newest), then live events (oldest → newest). No duplicates: each entry has a monotonically increasing id.

### Updated: `scripts/wsGateway.ts`

The boot script now creates a single `MemoryReplayStore` (configurable via `WS_REPLAY_MAX_PER_TOPIC`, default 1000), `psubscribe('*')`-attaches it to the pub/sub bus to record every event flowing through the gateway, and passes it to `createConnection` for each WS upgrade.

## TDD discipline

`tests/wsGateway/replay.test.ts` (9 tests) pins the store contract:

- record + since(0) round-trip
- preserves record order
- since-cursor filtering (returns only events after the cursor)
- empty result when cursor matches latest entry
- topic isolation (events on one topic don't leak into another)
- monotonic cursor ordering
- bounded retention with oldest-first eviction at `maxPerTopic`
- safe behavior when the cursor predates the eviction window

`tests/wsGateway/router.test.ts` adds 4 replay-specific tests:

- flushes missed events from the store on `subscribe(since: '0')`
- does not replay when `subscribe` has no `since` cursor
- still forwards live events after the replay flush completes
- skips replay cleanly when the store is omitted (back-compat with v0.0.35)

## Out of scope (deferred)

- **Cross-pod replay coverage.** Today the `MemoryReplayStore` is per-pod, so a client that reconnects to a different gateway pod from where it disconnected gets no replay (only the pod that received the original publish has the buffer). The Redis Streams adapter solves this; until then operators can either run a single gateway pod or accept the gap (clients still get live events; they just don't get the disconnect-window catch-up).
- **Client-side `since` cursor management.** This release ships the protocol; the in-tree Composer / SSE client does not yet read or send `since`. Adding the client wire-up unblocks the actual user-visible benefit; tracked separately.
- **Replay metadata (server time, sequence gaps).** The current entry shape is `{ id, event }`. Adding `recorded_at` and gap-detection is straightforward when needed; not blocking any current consumer.
