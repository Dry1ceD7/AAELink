# v0.0.40-alpha — thread-update events on the WS path

**Released:** 2026-05-19

The home shell's WS hook (v0.0.39) handled `message` and `deletion` events. This release adds `thread_update` — when a reply lands on a different gateway pod, or when a delete bumps the count down, the visible reply count on the root post updates immediately instead of waiting for the optimistic +1 bump that only fires when the reply arrives directly through the same connection.

Smallest scope I could carve: one event type wired in, one closeout. Reaction and presence/typing/read_state are queued for v0.0.41+ — they need slightly more care (reactions need an aggregate refetch; presence/typing live in their own components).

## What changed

`app/home/page.tsx` — the `connectWsCollab.onEvent` switch picks up a `thread_update` case:

```typescript
case 'thread_update': {
  const rootId = payload.root_id
  const next = payload.reply_count
  if (typeof rootId === 'string' && typeof next === 'number') {
    setPosts(current =>
      current.map(p => p.id === rootId ? { ...p, reply_count: next } : p)
    )
  }
  break
}
```

The defensive type checks mirror the same shape we use on `message` events: gateway frames carry `payload: PubSubEvent` (a discriminated union), but TypeScript's narrowing across our `switch` is one level deep and the inner fields can still be `unknown`-shaped depending on what published. Validate before applying.

## Out of scope (deferred)

- **Suppressing the optimistic +1 reply-count bump.** When a reply arrives via `message` on the same WS connection, `onIncoming` does a +1 bump; if the server later sends `thread_update` with the same authoritative count, the visible value is correct but briefly inconsistent in flight. The mismatch is sub-frame in normal latency. A future release can drop the optimistic bump on the WS path now that `thread_update` is reliable.
