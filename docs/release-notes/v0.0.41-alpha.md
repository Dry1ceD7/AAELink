# v0.0.41-alpha — multi-event WS sweep + bootstrap endpoint + pre-commit gates

**Released:** 2026-05-19

This release crams several roadmap items into one release instead of ticking them off one event-type per release. Five distinct wins:

1. **`reaction` events on the WS path** — close the user-visible feedback loop on remote reactions
2. **`read_state` events on the WS path** — multi-tab "mark as read" sync
3. **`channel_update` events on the WS path** — channel list refreshes when admins edit topic/purpose/etc.
4. **Bootstrap endpoint** (audit §2.3) — `GET /api/bootstrap` collapses 5 mount-time fetches into 1
5. **Pre-commit four-gates hook** (audit §2.6) — `scripts/git-hooks/pre-commit` runs the same gates CI runs, locally before each commit

## What changed

### `app/api/bootstrap/route.ts` (new)

```http
GET /api/bootstrap?workspace_id=<ws>
→ {
    user: { id, username, email, ... },
    teams: [{ id, name, display_name, is_system }, ...],
    workspace_id: <ws> | null,
    channels: [{ id, name, ..., unread_count, member_count }, ...],
    members: [{ id, username, first_name, ... }, ...]
  }
```

Server-side parallelizes the underlying queries via `Promise.all`. When `workspace_id` is omitted, returns just `user` + `teams` (the workspace-scoped sections come back empty arrays).

The home shell hits `/api/bootstrap` first on mount, then falls back to the existing fine-grained effects (`/api/workspaces`, `/api/auth/me`, `/api/collab/workspace-members`, `/api/channels`) which now act as refresh + safety net. When bootstrap succeeds — the common case — the user sees a single round-trip waterfall instead of five.

### `app/home/page.tsx` — three new WS event cases + bootstrap prefetch effect

```typescript
case 'reaction': {
  // Refetch aggregate via GET /api/messages/{id}; debounced 200 ms per
  // message_id to coalesce reaction bursts into one HTTP call.
  refetchReactionsDebouncedRef.current?.(payload.message_id)
  break
}
case 'read_state': {
  // Cross-tab "mark as read" — clear unread + mention counts locally
  // when the same user marks a channel read elsewhere.
  if (payload.user_id !== meRef.current?.id) break
  setChannels(current =>
    current.map(c => c.id === payload.channel_id
      ? { ...c, unread_count: 0, mention_count: 0 } : c))
  break
}
case 'channel_update': {
  // Refetch channel list (debounced 300 ms) — payload shape is opaque
  // (`payload: unknown` on the PubSubEvent), refetch is authoritative.
  refetchChannelsDebouncedRef.current?.()
  break
}
```

Both debouncers live in one `useEffect` keyed on `[activeTeamId, onReactionsUpdated]`; the WS event hook reads them through refs so its dep array stays minimal.

### `scripts/git-hooks/pre-commit` (new)

Plain bash. Runs `tsc --noEmit`, `eslint .`, `vitest run`, `next build` in order. Stops at first failure with a diagnostic. Documented activation:

```bash
git config core.hooksPath scripts/git-hooks
# or
ln -sf ../../scripts/git-hooks/pre-commit .git/hooks/pre-commit
```

Skip a single commit with `git commit --no-verify`. The CI workflow at `.github/workflows/ci.yml` runs the same gates so this is purely a "fail faster on the laptop" optimization — opting out doesn't change correctness.

## Operations notes

**No deployment changes required.** The bootstrap endpoint is additive; old clients keep using the fine-grained APIs. The WS event handling extends the existing path; deployments without `NEXT_PUBLIC_WS_GATEWAY_URL` continue with SSE/poll.

**To enable the local pre-commit hook:**

```bash
git config core.hooksPath scripts/git-hooks
```

**Hook performance:** the four gates take ~30 s on a recent laptop. If that's too slow per-commit, leave the hook off and rely on CI; the practical contract stays the same.

## Out of scope (deferred)

- **Replacing the fine-grained mount effects with bootstrap-only.** Current code keeps the per-endpoint effects as a refresh + fallback layer; cutting them out is a bigger surgery for a small additional gain. Tracked separately.
- **Bootstrap caching.** The endpoint is fully dynamic each call; in production a 30 s edge cache would absorb the burst at sign-in. Adds complexity (cache invalidation on workspace membership changes); deferred.
- **Reaction event burst protection beyond debounce.** A user adding 50 reactions in 200 ms still triggers one refetch (good). A pathological actor reacting on 50 different messages in 200 ms triggers 50 refetches (each debounced separately). Per-connection rate limiting on the gateway side covers this; tracked as gateway-side rate limiting.
