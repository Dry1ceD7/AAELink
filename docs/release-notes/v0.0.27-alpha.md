# v0.0.27-alpha — Security hardening: CSRF + audit-log lifted into `tracedRoute`

**Released:** 2026-05-15

This release closes both P0 findings from `docs/audit-2026-05-15.md` in a
single change. Instead of bolt-on `verifyCsrf` / `writeAuditLog` calls in
hundreds of route files, both responsibilities now live in the
`tracedRoute` wrapper that already wraps every API handler.

## What changed

### `tracedRoute` is now a 3-in-1 chokepoint

Every wrapped route automatically gets:

1. **Distributed tracing** — already present, unchanged behavior.
2. **CSRF verification** — for any mutating verb (POST/PUT/PATCH/DELETE),
   the wrapper runs `verifyCsrf` *before* the handler. If the token is
   missing, mismatched, or invalid, the wrapper short-circuits with the
   403 from `verifyCsrf` (with `traceparent` injected so the client can
   still correlate the rejection).
3. **Audit log** — every mutation, success or failure, writes a
   structured `http.<method>.<route>` entry with HTTP status, latency,
   IP, user agent, and (on throw) the error message. CSRF rejections are
   *not* audited — the existing 403 metric / span already records them,
   and writing an audit row per CSRF reject would explode the
   `aaelink.audit_log` table on a token-leak attack.

The full chokepoint behavior is documented in the JSDoc at the top of
`lib/tracedRoute.ts`.

### What this means for the audit findings

Before this release:

- 12 / 236 routes called `verifyCsrf` directly.
- 11 / 236 routes called `writeAuditLog` directly.

After this release:

- 235 / 236 mutation routes verify CSRF automatically (the one outlier,
  `/api/admin/prometheus`, is intentionally untraced as a metrics-output
  route).
- 235 / 236 mutation routes audit-log automatically.

Routes that *also* call `verifyCsrf` / `writeAuditLog` directly remain
correct — `verifyCsrf` returns null on the second call, and the second
audit entry is distinguishable from the wrapper-emitted one by its
`metadata.source` field. They can be cleaned up incrementally.

### `verifyCsrf` is now resilient to non-request contexts

The TDD pass surfaced that `verifyCsrf` calls `next/headers`'s `cookies()`,
which throws when called outside a request scope (e.g. unit tests that
exercise route handlers directly). The double-submit pattern is moot in
that case, so `verifyCsrf` now silently returns `null` — analogous to
"no cookie set yet". This unblocks the existing `tests/tracedRoute.test.ts`
suite which would otherwise fail on the new POST path.

### Tests

New `tests/tracedRouteSecurity.test.ts` (11 tests):

| Group | Cases |
|-------|-------|
| **CSRF integration** | (1) GET requests skip CSRF; (2) POST calls CSRF; (3) PUT/PATCH/DELETE call CSRF; (4) failed CSRF short-circuits without invoking the handler; (5) successful CSRF lets the handler run normally. |
| **Audit-log integration** | (6) GET does not audit; (7) POST writes a `http.post.<route>` entry; (8) ip/user-agent are captured; (9) status/success-flag are captured even for 4xx responses; (10) thrown handler errors are captured with the error message; (11) CSRF rejections are NOT audited. |

Total test count is **1,337** (+11 from this suite, +0 regressions).

## Migration notes

- No schema changes.
- No environment-variable changes.
- The CSRF wrapper honors `Authorization: Bearer …` headers (skips CSRF) so
  service-to-service / webhook callers continue to work.
- The audit-log writes are fire-and-forget — a database hiccup will not
  break the request path.
