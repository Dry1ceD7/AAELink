## Section 1 — Critical fixes (P0/P1, immediate impact)

### 1.1 Multi-node realtime fan-out is broken without Redis (P0 for production)

`lib/redisPubSub.ts` ships an `ioredis`-shaped abstraction with a `MemoryPubSub` fallback. With no `REDIS_URL` set, every Next.js node owns a private in-process `EventEmitter`. Two browsers connected to two different nodes behind a load balancer **never see each other's messages**. SSE reconnect re-polls and masks the bug for individual users; cross-session updates (typing, presence, message delivery to colleagues) silently fail.

`app/api/ws/route.ts` is a 426 `Upgrade Required` stub. The route documents the expected pattern (sidecar Node + `ws`) but doesn't implement it. SSE works as a fallback today; WS as a transport never opens.

**Fix shape.** Separate WS gateway service (Node + `ws`) behind the LB, terminating WebSocket upgrades, subscribing to Redis pub/sub, fanning out to connected clients. Set `WS_GATEWAY_URL` in production. Document `REDIS_URL` as **required** for any deployment with >1 Next.js node. **Without this, AAELink is single-node only.**

### 1.2 Inline `style={{...}}` blocks tax accessibility and theme portability (P1)

## Section 2 — Major architectural upgrades (long-term reliability)

### 2.1 Migrate the realtime layer to a dedicated WS gateway

SSE-only is fine for ≤200 concurrent users on a single node. Beyond that: per-domain SSE connection limits (browsers cap at 6), NAT timeouts, idle-disconnect issues. Slack uses long-lived WebSockets for the same reasons.

**Recommended stack.** Node.js + `ws` + Redis Streams (not just pub/sub — adds replay-on-reconnect for missed events). Run as a sidecar to Next.js pods with shared session backend. Backpressure: drop oldest-first per-channel queue at 1,000 events. Auth: re-validate session cookie on `upgrade`, then once per minute from inside the connection.

### 2.2 Move `lib/migrate.ts` from monolith to versioned migrations

`lib/migrate.ts` is 2,380 lines. Idempotent and back-compat, but every cold-start touches every `CREATE TABLE IF NOT EXISTS`. Nobody can safely diff a single function during code review.

**Fix shape.** Split into `migrations/0001_initial.sql`, `migrations/0002_…`, etc., with a tiny runner that records applied migrations in `aaelink.migrations`. Keep `ensureSchema()` as a back-compat wrapper that runs all unapplied migrations. Unblocks: down-migrations, dry-run plans, schema diffs in PRs, fresh-database CI integration tests.

### 2.3 Replace cold-start fetches with a single bootstrap endpoint

Home shell currently fires ~12 small fetches on mount (channels, members, prefs, theme, status, unreads, etc.). Median TTFB ≈ 200 ms each = 2.4 s waterfall.

**Fix shape.** Introduce `GET /api/bootstrap?workspace_id=…` that returns the same payload tree in one round trip. Server-side parallelizes the underlying queries.

### 2.4 Split `app/styles.css` into per-feature stylesheets

17,689 lines in one file. Build tools handle it; humans don't. Adopt CSS Modules or split into `app/styles/{base,sidebar,timeline,modal,admin,…}.css` with a single import in `layout.tsx`.

### 2.5 Adopt OpenAPI 3.1 generation for the 236-route surface

With `// keep:` markers now annotating intent on 65 routes, the metadata is rich enough to auto-generate. Tooling: `next-rest-framework` or a hand-rolled walker over `tracedRoute` exports. Output drives external consumer SDKs and makes the Slack-compat surface auditable.

### 2.6 Promote the post-write hook to a CI-side `pre-commit` check

The Superpowers four-gates hook fires after each batch of writes during agent sessions but only on the local dev machine. Add `pre-commit` script running the same gates so contributors who don't use the hook get the feedback loop. CI workflow already runs all four; `pre-commit` saves a round-trip.

## Strategic recommendation

§1.1 (multi-node Redis fan-out) and §2.1 (WS gateway) are coupled and form the natural next milestone. They unlock production scaling and lay groundwork for §3.1 (Huddle media plane) when infra arrives. Below them, §1.2 (inline-style reduction) is the right ongoing chore — pick one offender per release, drain over 4–6 months.

The Slack parity gaps in §3 are mostly *known and intentional*: the API surface is there; the runtime is the gap. The product can ship into a mid-market enterprise today (≤200 users / single node / SSE transport). §3.1, §3.2, §3.5 only become hard blockers at >1,000-user scale.
